# 第三章 chunk

#### 法律文档结构感知切分 + 规模估算

**实测结构扫描**（抽样 8 部门 24 个文件）：311 部法律天然按"条"结构化，有 6 种层级模式：


| 结构             | 示例                   | 说明             |
| -------------- | -------------------- | -------------- |
| 编→分编→章→节→**条** | 民法典 (2654段, 111k字)   | 仅1部，最复杂        |
| 编→章→节→**条**    | 刑法 (1401段, 74k字)、证券法 | 大型法律           |
| 编→章→**条**      | 反间谍法、旅游法             | 有编无节           |
| 章→节→**条**      | 宪法、保险法、个人信息保护法       | 有章有节无编         |
| 章→**条**        | 专利法、医师法、中医药法         | **最常见**，约 60%+ |
| **条**（无层级）     | 反分裂国家法、各类人大决定        | 很短的专门法         |


**关键结论：不需要复杂的切分策略**。所有文件的最小语义单元都是"第X条"（含"第X条之一"变体），正则 `第[一二三四五六七八九十百千]+条(之[一二三四五])?` 可 100% 精准定位。不存在"固定长度切分 vs 句子级切分 vs 结构感知切分"的选型问题——答案就是按"条"切。

每条 chunk 即一条法条。字段设计原则：不存可推导的、不存纯冗余的、不存仅一部法律用到的。

## 字段详解



### `chunk_id` — 全局唯一标识

- **类型**: `str`
- **格式**: `{law_name}#{article_no}`
- **分隔符**: `#`（法律名不含此字符，安全）
- **用途**: Ch4 FAISS 索引的 string→int 映射 key；Ch11 `lookup_article(law_name, article_no)` 的 O(1) 查找 key；增量更新时的覆盖主键
- **使用环节**: Ch4 建索引、Ch8 多轮指代消解、Ch11 Agentic 工具调用



### `law_name` — 法律全称

- **类型**: `str`
- **示例**: `"中华人民共和国刑法"`、`"中华人民共和国民法典"`
- **来源**: .docx 文件名去掉 `_YYYYMMDD.docx` 后缀
- **使用环节**: 全链路



### `article_no` — 规范化条号

- **类型**: `str`（不是整数，因为存在"之一"变体）
- **格式**: `^\d+(之[一二三四五])?$`
- **示例**: `"1"`、`"264"`、`"133之一"`、`"17之一"`
- **来源**: 正则匹配 `第[一二三四五六七八九十百千零]+条(之[一二三四五])?` → cn2arabic 转换
- **使用环节**: 全链路



### `article_no_sort_key` — 自然排序键

- **类型**: `[int]`，1-2 个元素的数组
- **格式**: `"264"` → `[264]`；`"133之一"` → `[133, 1]`；`"133之二"` → `[133, 2]`
- **用途**: 字符串 `article_no` 无法排序（`"2" > "10"`），此数组字典序 = 法条在文本中的真实顺序
- **使用环节**: Ch5 检索结果排序、Ch8 多轮相邻法条定位
- **为什么不是独立字段？** 因为检索结果需要展示 `article_no` 而非 sort_key，sort_key 是内部排序用



### `content` — 法条正文

- **类型**: `str`
- **内容**: 法条纯文本，不含层级标题前缀、不含页码残留、不含 `（删去）` 占位符
- **用途**: 稠密向量（BGE）的输入文本；BM25 的文档字段；Ch9 拼入 prompt 的上下文；Ch11 工具返回
- **使用环节**: Ch4/5/9/11
- **注意**: BM25 索引时可以额外拼接 `law_name` + hierarchy 关键词到索引文本中（由 BM25 索引代码动态生成，不存入 JSONL）



### `token_count` — MiniMind token 数

- **类型**: `int`
- **来源**: MiniMind-6400 tokenizer 对 `content` 的实际编码结果
- **用途**: Ch9 context budget 实验（512/768/1024 三档精确分配），精确知道"塞 N 条法条会不会超预算"
- **使用环节**: Ch9
- **注意**: 这是 MiniMind 专属指标。`char_count` 保留作为模型无关的通用指标



### `char_count` — 字符数

- **类型**: `int`
- **来源**: `len(content)`
- **用途**: 模型无关的通用长度指标；BM25 文档长度归一化；快速估算
- **使用环节**: Ch5/9



### `department` — 所属法律部门

- **类型**: `str`，枚举值 8 个
- **枚举**: `刑法 | 民法商法 | 行政法 | 经济法 | 社会法 | 生态环境法 | 诉讼与非诉讼程序法 | 宪法及宪法相关法`
- **来源**: 文件所在目录名
- **用途**: Ch5 部门过滤检索；Ch7 路由目标
- **使用环节**: Ch5/7
- **注意**: 部门名不是法律名。例如"行政法"目录下有多部法律（医师法、治安管理处罚法等），不能当 law_name 用



### `effective_date` — 遗留文件名日期（不等于施行日期）

- **类型**: `str`，格式 `YYYY-MM-DD`
- **来源**: 文件名 `_YYYYMMDD.docx` 后缀
- **当前语义**: 旧索引兼容字段；其具体法律事件含义未逐条核验，不能作为施行日期。
- **使用限制**: 不用于时效过滤、历史版本消歧、模型证据包或中文回答；未来如需时效能力，必须由权威元数据单独补充。



### `hierarchy` — 层级结构

- **类型**: `dict`，动态键
- **可能的键**: `编`、`分编`（仅民法典）、`章`、`节`
- **值**: `"第X编/章/节 标题"` 格式的字符串，或 `null`
- **无层级法律**: `{}`（如反分裂国家法、各类人大决定，全文仅若干条，无编章节结构）
- **来源**: 扫描全文 `第X编`/`第X分编`/`第X章`/`第X节` 行，根据法条文本位置判定归属
- **使用环节**: Ch5 检索层级加权（如章名匹配加分）；Ch9 prompt 按层级分组展示
- **设计决策**: 不固定 schema，有什么层级存什么。`分编` 仅民法典有（311 部中仅此 1 部），其余法律不设此键

## 附则处理

跳过"附则"章的全部条文（如"本法自 X 年 X 月 X 日起施行""原 X 法同时废止"）。附则条文 content 极短（通常一行），且对法律检索查询无实质价值，纳入只会污染 embedding 质量和检索结果。

## citation 格式化（不存储，使用时动态生成）

```python
def format_citation(law_name: str, article_no: str) -> str:
    if '之' in article_no:
        main, suffix = article_no.split('之', 1)
        return f"《{law_name}》第{main}条之{suffix}"
    return f"《{law_name}》第{article_no}条"

# "中华人民共和国刑法", "264"      → "《中华人民共和国刑法》第264条"
# "中华人民共和国刑法", "133之一"  → "《中华人民共和国刑法》第133条之一"
```

## 已知限制

- **附件/附表不提取**：刑法附件一/二（罪名表）不受 `第X条` 正则匹配，不在索引中。查询"组织出卖人体器官罪在不在刑法里"会漏，v2 可补充
- **chunk_id 不含日期**：当前 311 部均为单一最新版本，不存在同法条多版本碰撞。未来多版本时扩展为 `"{law_name}#{doc_version_date}#{article_no}"`
- **FAISS ID = JSONL 行号**：不是 chunk_id。Ch4 构建时需维护 `chunk_id → faiss_position` 映射 dict

## 切分方案设计思路

以下记录从"拿到 311 个 .docx"到"产出 22,201 条法条级 chunk"过程中，每个关键决策的思考过程。

### 切分粒度：为什么按"条"切而不是固定长度/句子级

通用 RAG 的切分策略是固定 token 数（512t）+ overlap（50t），在 chunk 边界处智能断开。法律文档有天然的结构优势——"第X条"是中国法律的最小完整语义单元。一条法条定义了一个罪名、一个要件、一个量刑规则，切分比句子更粗、比较落更细，恰好落在语义自包含的粒度上。

**抽样验证**：实际扫描 8 部门的 24 个文件后确认，311 部法律 100% 用"第X条"作为基本单元。不需要做"固定长度 vs 句子级 vs 结构感知"的对比实验——答案就是按条切。唯一需要实验验证的是"切完以后 recall 是否达标"，用 30 条手工 QA 快速验证即可，不需要在那之前浪费时间去实现 3 种切分策略。

### 为什么必须处理"之一"

刑法修正案通过"第X条之一"的形式在原文中插入新条款，而非重新编号。例如，在"第 133 条 交通肇事罪"后面，修正案插入了"第 133 条之一 危险驾驶罪"。如果正则只匹配 `第[数字]+条`，`第 133 条之一` 的正文会被吞为第 133 条的一部分，然后第 133 条变成一条超长的、包含两个无关罪名的大 chunk。

危险驾驶罪（133条之一）是司法实践中最高频的罪名之一，索引不能包含它 ≈ 检索系统在法律高频场景下残废。

实际实现中，正则扩展为 `第[一二三四五六七八九十百千零]+条(之[一二三四五六七八九十]+)?`，`cn2arabic` 只转换主条号的数字部分，"之"后的中文数字保留原样。最终 article_no 为 `"133之一"`，自然排序键为 `[133, 1]`——字典序自动让"之一"紧跟在主条号后面。

### cn2arabic 的两次重写

这是整个提取过程中唯一出过严重 bug 的环节。

**第一版（反向逐字累加算法）**：从右到左扫描，遇到"十""百""千"类量级标记时乘以当前基数。测试用例 `一→1, 十→10, 十九→19` 全部通过，看起来正确。但它对 `二十` 返回 30、对 `一百` 返回 200——量级标记在反向扫描时的叠加逻辑有数学错误。由于批量跑 311 部法律无法人工逐条验证，这个 bug 存活了整整两轮。

**发现方式**：独立子 agent 审计报告指出"民法典预期 1260 条但只提取到 1062 条，缺少约 200 条"。排查发现含"零"的条号（`第一千零一条` 等）匹配失败，进一步追查发现反向算法对所有"百"级数字计算偏移。根因是两个叠加的 bug：正则字符类缺 `零` + 算法对量级标记处理错误。

**第二版（正向逐字累加算法）**：从左到右扫描，数字（一~九）暂存到 current，遇到量级标记（十/百/千）时 current × 量级 → 累加到结果。`1005` → `一千零五` → 一(1)→千(1×1000=1000)→零(0)→五(5)→1005。全程正向，无状态回退。

验证方式：用已知法条数的法律做端到端验证。民法典精确 1260/1260，刑法 452/452，公司法 266/266。所有匹配的预期值都精确命中。

### hierarchy 为什么用动态键

民法典有 `编→分编→章→节→条` 五层，刑法有 `编→章→节→条` 四层，医师法只有 `章→条` 两层，反分裂国家法只有 `条`。如果 schema 固定为 `{编, 分编, 章, 节}`，311 条中的 310 条都有多余的 null 字段。动态键让每条 chunk 只存它实际拥有的层级，null 键直接不出现。

实现方式：扫描全文中的 `第X编`/`第X分编`（仅民法典）/`第X章`/`第X节` 行，记录每个标题的文本位置。提取法条时，根据法条的文本起始位置，判定位居哪些标题之后，填充对应的 hierarchy 键。

### 构建后质量修复：hierarchy 泄露与尾部残留

这两个问题是在用检索评估结果反向审计 chunk 质量时发现的，都是 `extract_chapters()` 和 `clean_article_content()` 的正则不够严谨导致的。

**hierarchy 数据泄露（197 条，占 0.9%）**

`extract_chapters()` 的四个层级标题正则没有行首锚定。法条正文中经常出现「依照本法第三章的规定」「适用前款第(一)项第四章的规定」等交叉引用——这些不是层级标题，却被正则匹配并写入了 hierarchy 字段。

例如宪法第 116 条的 hierarchy 错写为 `{"章": "第3章 第五节规定的地方国家机关的职权，同时依照宪法、民族区域自治法和其他法律规定的权限..."}`——把 40 多字的法律正文当成了章标题。这 197 条错误 hierarchy 会影响 Ch5 层级过滤的准确性。

**修复**：给四个正则各加 `(?<=\n)` 行首锚定。只有换行后紧跟的 `第X编/章/节` 才是真正的层级标题行：

```
旧: r'第([一二三四五六七八九十百千零]+)章\s*[　 ]?\s*([^\n]{2,40})'
新: r'(?<=\n)第([一二三四五六七八九十百千零]+)章\s*[　 ]?\s*([^\n]{2,40})'
```

**content 尾部残留（139 条）**

`clean_article_content()` 的 `HIERARCHY_HEADER` 最初按 `\n`（单换行）匹配尾部残留标题。但中国法律 .docx 的层级标题前后通常有多个空行，实际残留格式是 `\n\n第二章　行政赔偿`。单换行正则只能清理 `\n第X章`，漏掉了双换行模式的 139 条。此外还有 5 条极端案例——章标题本身跨了两行（如「第四章　犯罪嫌疑人、被告人逃匿、死亡案件\n违法所得的没收程序」），单行正则 `[^\n]*$` 完全无法匹配。

**修复**：两处改动——

1. `HIERARCHY_HEADER` 的 `\n` 改为 `\n+`（匹配连续换行）
2. 针对跨行标题，在构建后统一用 `\n\n第` 定位最后一个层级标题位置，从该处截断

**验证方式**：两个指标均归零确认——hierarchy 字段最长值 < 30 字（197→0）、content 尾部 `\n\n第X编/章/节` 残留 139→0。所有 edge case（5 条跨行标题）单独核验。

> 教训：层级标题的识别必须在 `(?<=\n)` 行首锚定下进行，这是区分「真标题行」和「正文交叉引用」的唯一可靠信号。仅靠正则匹配 `第X章` 而不检查上下文位置，会大量误抓。



### 被删除的 4 个字段及其删除理由


| 删除的字段                  | 理由                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| `citation`             | `f"《{law_name}》第{article_no}条"` 是零成本字符串插值，存储 23k 条 × ~30 字符 = ~700KB 浪费。且 citation 格式可以后期统一修正，存了反而可能不一致 |
| `hierarchy_path`       | 可从 `law_name` + `hierarchy` 实时拼接。BM25 需要时在索引构建时动态生成，不存入 JSONL                                           |
| `search_text`          | BM25 索引代码决定是否拼接 hierarchy 关键词到文档文本中。存入 JSONL 意味着如果后续想改拼接方式需重建 23k 条                                     |
| `article_count_in_law` | 需要时可从 `article_index.jsonl` 中按 law_name group by 数出，不需要每条冗余存储                                           |
